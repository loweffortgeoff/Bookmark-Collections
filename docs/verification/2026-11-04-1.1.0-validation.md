### Mac UI suite failure, 2026-11-04 (root cause found, harness fixed)

Geoff reports this has recurred since the app's first builds. Repo history agrees: an empty accessibility tree (Oct 23), paywall cases unable to find the window (Nov 3, worked around with a `--` launch-argument separator), and every case on the 06:12 run (`build/step6-mac-ui.xcresult`). Under XCTest the app launched with a menu bar and no window.

**Root cause: AppKit window restoration with saved state that has no window.** Side: Apple platform behavior, triggered by our test setup. Not an app defect. Machine: Mac mini, macOS 27.2, Xcode 27.2.

- Saved window state belongs to the bundle ID. Every Tucked copy on this Mac shares it: the Debug test build, the `~/Applications` Release copy, and the TestFlight copy in `/Applications`. `talagentd` stores it.
- Evidence from the 06:09 failing run (unified log): at 06:09:11 the `~/Applications` copy (pid 88677) closed its window and stayed in the menu bar. `talagentd` logged `deleteSnapshotForWindowID` for it. At 06:09:47.600, when the first test launch (pid 9130) connected, `talagentd` logged "Service already exists for url … Eliding writes from previous service" for pid 88677. So both processes used the same state directory. Pid 9130 then logged `shouldRestoreState=1 hasPersistentStateToRestore=1` and restored no window record.
- A passing launch logs the same line and then `restoreWindowWithIdentifier: identifier=library`. The only difference is whether the shared state has the library window.
- Under XCTest, a launch that restores windowless state shows no window. A launch with `open` shows "All Items" even with the same state. That is why the earlier `open` check passed.
- The problem keeps itself going. XCTest launches never write window records, and XCTest kills each app, so the windowless state stays for the whole run and for later runs. A clean state lasts until some copy outside XCTest closes its window and dies while in the menu bar.
- Reproduced on demand: launch the Debug build with `open -n … --args -ui-testing`, wait 15 s, close the window, wait 15 s, then `kill -9`. `talagentd` logs `writeRecords` and `deleteSnapshotForWindowID`. Next, `testAppLaunches` and `testSnippetsDestinationShowsOnlyTextItems` fail with the same errors as at 06:12 (only these two cases were run unfixed).

**Second trigger, same symptom: a bare launch-argument value.** Under XCTest, a bare value such as `YES`, `NO` or `0` without a leading `--` stops the initial window from opening. The mechanism is not confirmed: the log shows no file-open event (it may be AppKit reading the value as a file to open). Proof of the symptom (06:49 run): with `-ui-testing -ApplePersistenceIgnoreState YES` and restoration off (`hasPersistentStateToRestore=0` on every launch), 13 cases failed with no window. The paywall cases, which put `--` first, passed. This matches the Oct 23 note (numeric `-free-limit 0`) and the Nov 3 `--` workaround. Those were this trigger, not saved state.

**Fix (harness only):** `BookmarkCollectionsUITests/TuckedLaunch.swift`. On Mac every UI test launch starts with `--`, then its own arguments, then `-ApplePersistenceIgnoreState YES`. The paywall tests already start with `--` and now add the same flag. With the state poisoned, fixed launches log `hasPersistentStateToRestore=0` and show the window. The flag also stops the tests from writing shared state. New Mac launch arguments with values must go after `--`. iOS launches are unchanged.

**Separate flake found during verification:** one poisoned full run (06:59) failed `testEmptyRecentlyDeletedRequiresConfirmation` with the window present. At the default 900 x 450 window the sidebar overflows. The Recently Deleted row (y 762.5–784) ends below the sidebar's scroll area (ends at 781), and the click at its center (y 773) did not select it. The clipped row is the likely cause, not a proven one. The test now scrolls the sidebar first when a row is clipped at the bottom; the row then sits at y 739.5–761. The test passed 20 of 20 times alone before this change, so the flake is rare, and two clean runs do not prove the scroll fixes it.

Ruled out or corrected:

- The `c4c2747` result does not clear the menu bar commit for the reason first given. Any commit fails once the state has no window. The menu bar commit made the trigger more common, because closing the window no longer quits the app.
- Quitting the `~/Applications` copy did not help because the windowless state was already written. That copy was a trigger, not a constant cause.
- "No saved window state" was checked in the wrong place. `~/Library/Containers/com.loweffortapps.BookmarkCollections` does not exist on this Mac; `talagentd` serves the state, so its path is not visible in the log.
- Spaces or displays: no. `onCorrectWorkspace=0` shows in passing launches too.
- TCC or Accessibility permission: no. Accessibility queries work, and the suite passes with the same permissions once restoration is off.
- XCTest launch arguments or environment: the app gets only `-ui-testing`. XCTest's launch path matters only because it opens no default window when restored state has none.
- `MenuBarExtra` race: no. The status item comes up the same way in passing and failing launches.
- Oct 23 and Nov 3: these match the bare-value trigger above. Their own logs are gone, so this is inferred from the arguments they used.

Possible user-facing follow-up (not checked): a user who closes the window and whose app is then killed (crash, logout, update) may relaunch into restored windowless state. A normal `open` launch still showed the window here, so the risk looks small. Login-item and crash-relaunch paths are not checked.

Install the Mac Release build to `~/Applications/Tucked.app` only. Do not replace `/Applications/Tucked.app`; it is the App Store copy.
